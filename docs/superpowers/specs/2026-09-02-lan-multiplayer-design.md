# 局域网联机对战（含 AI 替补） — 设计

## 背景与目标

SpaceFlightChess 目前只有一种对局模式：本地玩家选一个阵营，另外三个阵营固定由 `PlaneAi` 驱动。本次要加入**同一局域网内的多人联机**，并且——这是用户提出的核心约束——**人数不足时空缺的座位由 AI 替补**，不要求凑满 4 个真人才能开局。

参考项目是同一工作区的 `SpaceGomoku`，它已经落地并验证过一套「NSD 服务发现 + TCP 直连 + host 权威」的局域网联机方案（见 `../../../SpaceGomoku/docs/superpowers/specs/2026-08-25-lan-multiplayer-design.md`）。本设计沿用它的骨架与全部技术前提（不引第三方服务、不做 NAT 穿透、不做加密鉴权），但在三个地方必须重新设计，因为飞行棋和五子棋的结构差异是实质性的：

1. **4 个座位而不是 2 个**。房间是一个四席的大厅，每席可以是本地玩家、远程玩家或 AI。
2. **骰子是一个随机源**。五子棋没有任何随机性，落子坐标就是全部信息；飞行棋每一回合先摇骰再走子，随机数必须由权威方产生并广播，否则各端立刻分叉。
3. **一步棋带一段长动画**。飞行棋走子是逐格 1 秒的动画，现有 `BoardStage` 用 `isTurnBusy` 门禁做回合串行化。这个门禁要在跨网络的四端之间保持正确。

### 范围

- **联机范围**：同一局域网（同一 WiFi / 路由器）下最多 4 台设备直连。不做跨网络互联网对战——理由与 `SpaceGomoku` 完全相同（信令交换无法在 VR 头显里手动完成；NAT 穿透需要 STUN/TURN，而用户明确排除任何第三方服务或自建服务器）。
- **发现方式**：NSD 自动发现房间列表为主，手动输入房主 IP 为兜底。兜底路径不是可选项：`SpaceGomoku` 已实测确认 PICO 模拟器所在的 QEMU 用户态 NAT 不转发任何方向的组播，且本工作区已确认模拟器与真机之间联机完全不通，mDNS 在若干真实网络环境下也会被 AP 隔离/访客网络/部分 mesh 路由挡掉。
- **权威模型**：创建房间的一方（房主）是唯一权威。它持有真骰子，裁决全部走子请求，驱动所有 AI 座位。客户端只镜像房主的广播。
- **AI 替补有两层含义**：(a) 开局时仍空着的座位固化成 AI；(b) 对局中掉线的玩家在超时后由 AI 托管，重连回来可以拿回控制权。
- **同步模型**：事件广播 + 各端确定性重放 + 每步校验和（下方「同步模型的选型」一节说明为什么）。

## 不做的事（YAGNI）

- 不做互联网匹配 / matchmaking，不引入任何第三方服务（Firebase、Photon 等）或自建服务器。
- **不做房主迁移**。房主是唯一权威、NSD 广播方和 `ServerSocket` 持有方，它离开就没有权威可言。房主迁移需要选举、状态转移、重新广播，是明显更大的另一个功能。房主掉线即结束对局。
- **不做进程被整个杀掉/重启之后的对局恢复**。重连只处理连接层面的瞬断，前提永远是掉线一方的 App 进程还活着。
- **不做动画 ack**。房主不等客户端播完动画再推进，否则全场节奏被最慢的设备拖住，还要引入 ack 超时这一整类新问题。
- **不做应用层心跳**。断线检测只靠 socket 读写抛出的 `IOException`，局域网环境下这已经够用（与 `SpaceGomoku` 同）。
- 不做观战、聊天、语音、战绩统计、房间密码。
- 不做加密 / 鉴权。局域网内的邻近设备直连，不是需要防御的公网服务。
- **不做 co-location / 共享空间锚点**。四个人各自看自己面前的一块棋盘，只同步棋局逻辑状态，不同步物理空间。棋盘的摆放距离、朝向、缩放仍由各端本地决定。
- **不改 `GameEngine` 的对局规则或既有公开 API**。唯一的改动是给 `forceState` 加一个默认参数（见「协议」一节末尾），源码向后兼容。
- 不做「继续等待 / 结束对局」的重连超时选择弹窗（`SpaceGomoku` 有）。见「掉线与 AI 托管」一节：这里掉线不阻塞其他人，因此没有必要逼任何人做这个选择。

## 同步模型的选型

`grep -n "Random" app/src/main/java/tech/illusion/spaceflightchess/game/*.kt` 只命中 `DiceEngine.kt` 一个文件——**`DiceEngine` 是整个 `game/` 包里唯一的随机源**。而且它是 `open class` 且构造注入，单测早就在用脚本化子类喂固定序列。

这条事实决定了整个设计：**只要骰子点数由房主广播，四端的 `GameEngine` 就是完全确定性的**，同一串输入必然推出同一个局面。`legalMoves(state, team, roll)` 是纯函数，`resolve(state, move)` 是纯函数，胜负判定、摇 6 额外回合、三连 6 罚回机库、无合法走法自动过手全部由这两个纯函数加一个内部计数器推出。

在这个前提下考虑过三个方案：

- **A. 纯事件广播**。房主只发 `ROLLED` 和 `MOVED`，各端本地重放。带宽最省、实现最简。缺点是一旦某端真的分叉（版本不一致、消息被截断），没有任何机制能发现，四个人会一路看到不同的棋盘。
- **B. 每步全量状态快照**。永不分叉，但客户端仍然需要知道「这一步该怎么走动画」，所以还得同时发 `Move`——B 实际上等于 A 再加一份快照，是纯增量成本。
- **C. A + 每步带一个状态校验和**（**选定**）。消息仍是 A 的两条，`MOVED` 多带一个由局面算出的短校验和；客户端 apply 完自己算一遍，对得上什么都不做，对不上才请求一次全量 `SYNC`。

选 C。多出来的代码只有一个纯函数和一条极少触发的兜底消息，换来「分叉可被发现且能自愈」。飞行棋的状态比五子棋复杂得多（16 架飞机 × 待飞/在途/归家小道/终点 + 僚机叠放），静默分叉在这里比五子棋危险，而排查一个只在多设备对局中复现的分叉会非常痛苦。

## 架构

### 分层

沿用项目现状：`game/` 纯 Kotlin 规则层不动；新增 `net/` 包（纯 Kotlin、零 Android 依赖、可单测）；持有 `NsdManager` / `Socket` 生命周期的类放 `content/`。

### 一处有边界的结构整理

`BoardStage.kt` 已经 639 行，而且「推进一个回合」这件事目前散在三处各写一遍：`rollAndAdvance()`（骰子 + AI 走子）、飞机点击处理器（人类走子）、AI 轮询 driver。联机会引入第四个来源（网络广播）。照现状继续摊，四条路径各自维护一遍 `isTurnBusy` 门禁 + 动画播放 + `publish()`——而 AGENTS.md 记录了这个门禁历史上已经出过两次问题（keyed effect 导致摇 6 后不再触发；门禁卡死把游戏整个锁死）。

因此把四个来源收敛成**一条命令队列 + 一个串行执行器 + 一个门禁**：

```
                本地骰子点击 ─┐
                本地飞机点击 ─┤
        AI driver（仅房主/单机）─┼──▶  Channel<TurnCommand>  ──▶  唯一的执行器
              网络收到的广播 ─┘                                  （唯一的 isTurnBusy
                                                                  + 动画 + publish）
```

这不是顺手重构：联机本来就需要第四条来源汇入同一个门禁，而合并的副产品是单机现有的两条重复路径也变成一条。**回合串行化的正确性从此只有一个地方需要看对。**

`TurnCommand` 是纯数据，放 `net/`：

```kotlin
sealed interface TurnCommand {
    /** value=null → 本地真骰子决定（单机/房主）；非 null → 用房主广播的点数（客户端）。 */
    data class Roll(val team: Team, val value: Int?) : TurnCommand
    /** pieceIndex 是候选 Move 的代表棋子下标；各端本地在 legalMovesForPendingRoll() 里查回完整 Move。 */
    data class Apply(val team: Team, val pieceIndex: Int) : TurnCommand
    data class Resync(val state: GameState, val consecutiveSixes: Int) : TurnCommand
}
```

### 与 SpaceGomoku 的一处有意分歧

`SpaceGomoku` 的 `LanMatchHost` 自己持有一个 `GameEngine`。这里**不**这么做：三种角色（单机 / 房主 / 客户端）都只有 `BoardStage` 里那一个 engine，网络层退化成纯粹的传输 + 协议，只负责往队列里塞 `TurnCommand`、往外发消息。这样 `PlaneAi` 及其调用代码一个字都不用改，只是加一个「仅单机或房主时启动」的门。

## 协议

一行一条纯文本，换行定界，不引序列化库——消息类型少，且纯文本行让 Mac 侧的陪练脚本成为可能（见「验证计划」）。`decode` 对任何无法解析的输入返回 `null` 而不抛异常：socket 来的是不可信输入。

### 房主 → 客户端

| 消息 | 载荷 | 说明 |
|---|---|---|
| `WELCOME` | 你的队伍 + 完整座位表 | 连上后第一条 |
| `LOBBY` | 完整座位表 | 有人加入 / 离开 / 换座时重发 |
| `START` | 完整座位表（空位已固化为 AI） | 房主点开始 |
| `ROLLED` | 队伍 + 点数 | 权威骰子结果 |
| `MOVED` | 队伍 + 代表棋子下标 + 校验和 | 走了哪一步 |
| `SEAT` | 队伍 + 状态（在线 / 等待重连 / AI 托管） | 座位状态变更 |
| `SYNC` | 16 架飞机 + 当前队伍 + 连 6 计数 + 座位表 | 全量对齐 |
| `ENDED` | 原因 | 对局结束 |

### 客户端 → 房主

| 消息 | 载荷 | 说明 |
|---|---|---|
| `JOIN` | 显示名（设备型号） | 连上就发 |
| `SEAT_REQ` | 目标队伍 | 请求换到某个颜色 |
| `ROLL_REQ` | — | 请求摇骰（不本地摇） |
| `MOVE_REQ` | 代表棋子下标 | 请求走子（不本地 apply） |
| `RESYNC_REQ` | — | 校验和对不上，要全量 |
| `LEAVE` | — | 主动离开 |

### 共享常量（`RoomState.kt`）

两侧都要用到、且必须一致的值集中放一处（`SpaceGomoku` 记录过「两份私有副本靠运气保持一致」的教训）：

| 常量 | 值 | 说明 |
|---|---|---|
| `SERVICE_TYPE` | `_spaceflightchess._tcp.` | NSD 服务类型 |
| `MATCH_PORT` | `47780` | 固定端口，不用 `ServerSocket(0)` 的临时端口——手动输入路径下让玩家只需要敲 IP，不用再敲五位端口号。代价是同一台设备开不了两个房间，且房主结束一局后要立刻重新绑定同一端口，所以绑定前必须设 `reuseAddress`（否则 `TIME_WAIT` 会让本次会话的第二次建房失败） |
| `MAX_CLIENTS` | `3` | 4 席减去房主自己 |
| `RECONNECT_GRACE_S` | `15` | 轮到掉线玩家时的等待窗口，判断值 |

**「第一个空位」的顺序**在全文中一律指 `Team.entries` 的声明序（红 → 黄 → 蓝 → 绿），`SeatAssigner` 与其单测都以此为准。

### 为什么 `MOVED` 只需要一个棋子下标

`legalMoves(state, team, roll)` 是纯确定性函数，四端算出的候选列表完全一致。核实过它的构造：机库起飞（仅 `roll == LAUNCH_ROLL`，只对 `InHangar` 的棋子）、僚机叠放（同格的多架合并成一个 `Move`，代表是组内最小下标）、单机（其余在途棋子）——三条分支的棋子集合互不重叠，**同一个代表下标在候选列表里最多出现一次**。所以一个整数就能唯一还原整个 `Move`，包括 `groupPieceIndices` 和 `bounceWall`，不必把 `Move` 整个序列化。三连 6 的罚回机库走的是同一个 `legalMovesCache`，形状一致，同样适用。

客户端点到僚机里的第二架时，本地先在候选里找到 `groupPieceIndices` 包含它的那条，发**代表**下标。

### 校验和

`StateChecksum.of(state: GameState): Int` 对 16 个 `PieceState` 按固定顺序（队伍声明序 × 棋子下标）加上 `currentTeam` 做 FNV-1a。不用 `hashCode()`——自己写死算法才能保证跨端一致、可单测、且改动时会被测试抓到。

### 为什么 `forceState` 要加一个参数

`SYNC` 要能真正把客户端拉回一致，就必须带上 `consecutiveSixes`（连摇 6 的计数）。现有的 `forceState` 无条件把它清零：如果正好在某人连摇 6 的中途 `SYNC`，客户端计数归零而房主没有，之后房主触发「三连 6 罚回机库」、客户端不会，两边永久分叉。

因此 `fun forceState(newState: GameState, consecutiveSixes: Int = 0)`。默认值保证现有调用（测试与设备验证脚手架）行为完全不变。

另外，**`SYNC` 只在房主处于 `Phase.AWAITING_ROLL`（回合之间、没有待决点数）时才发送**，因为 `forceState` 的语义本来就是跳到回合起点。不在一步棋的中途同步。

## 座位与大厅

### 座位的三种占据方式

| 显示 | 含义 |
|---|---|
| 本地玩家 / 远程玩家 | 有人坐着，名字来自设备型号 |
| 空 | 没人。标注「开局后由 AI 接管」 |
| AI | **只在开局那一刻产生**——房主点开始时，仍空着的座位固化成 AI |

大厅里不存在「和 AI 换座」这种操作：空位就是空位，AI 是开局瞬间才落定的。

### 流程

```
StartPanel（改）
  ├─ 选阵营（现有 4 色选择器，原样保留）
  ├─ [ 开始游戏 ]  ← 单机，行为完全不变
  ├─ [ 创建房间 ]  → 带着刚选的颜色进大厅，直接坐那个位
  └─ [ 查找房间 ]  → 房间列表 / 手动输地址
                          ↓
                     连上 → 房主自动把你安排到第一个空位
                          ↓
              ┌─────────────────────────────────┐
              │  大厅面板                        │
              │  🔴 红  Zohar（房主）            │
              │  🟡 黄  你          ← 点其他空位 │
              │  🔵 蓝  空 · 开局补 AI    即可换 │
              │  🟢 绿  空 · 开局补 AI          │
              │  ─────────────────────────────  │
              │  房主：[ 开始游戏 ] [ 解散房间 ] │
              │  其他：等待房主开始…  [ 离开 ]   │
              └─────────────────────────────────┘
                          ↓ 房主点开始
              空位固化成 AI → 各端本地 configureSeat(自己的颜色)
              → 棋盘转到自己面前 → 进入对局
```

### 判断与理由

- **加入时自动落在第一个空位**，而不是强制先选颜色。房主可能随时点开始，「还没选完就开局」是真实会发生的坑；自动落座保证任何时刻每个人都有位置，想换再换。
- **换座由房主唯一裁决**。客户端发 `SEAT_REQ`，**永远不预先改自己的座位显示**，等房主广播的 `LOBBY` 座位表回来才变。两个人同时点同一个空位时先到先得，后到的看到那格已经是别人了——不需要任何冲突协商逻辑。
- **房主自己也走同一套换座机制**，没有特权路径。
- **每个人的棋盘按自己的颜色转向自己**。复用现有 `BoardGeometry.configureSeat` 与 `SEAT_ANIMATION_STEPS` 转桌动画，一行不用改。四个人看到同一局棋、四个不同的座位视角——这本来就是现有单机选阵营的行为，联机只是让四个人各选各的。
- **房间列表显示 `n/4` 数的是真人数**，不含将来会补的 AI。
- **房主的大厅面板底部显示自己的局域网 IP**，供对方手动输入。

## 对局同步

### 三种角色下的同一条执行器

| 角色 | 谁往队列塞命令 |
|---|---|
| 单机 | 本地点击 + AI driver |
| 房主 | 本地点击 + AI driver + 收到客户端请求后自己裁决 |
| 客户端 | 收到房主的 `ROLLED` / `MOVED` 广播（本地点击只发请求，不入队） |

**客户端本地点击不入队，是这套设计的核心不变式**：客户端的棋盘状态只由房主的广播驱动，永远不会自己先走一步导致分叉。与 `SpaceGomoku`「不在本地 apply，等 `MOVE_CONFIRMED` 回来」是同一条原则。

### 一个完整回合（远程玩家 B 执黄）

```
B 点骰子 ──ROLL_REQ──▶ 房主校验（AWAITING_ROLL 且 currentTeam == 该连接的座位）
                            │
                            ├─ 入队 Roll(YELLOW, null) → 执行器 engine.roll() = 4
                            │
                            └─ 先广播 ROLLED YELLOW 4 ──▶ 所有客户端
                                                            入队 Roll(YELLOW, 4)
                            ↓ 之后才播自己的骰子动画          ↓ 各自播骰子动画
                       （四端并行播，不互相等）

B 点飞机 ──MOVE_REQ 2──▶ 房主校验 → 入队 Apply(YELLOW, 2)
                            ├─ 先广播 MOVED YELLOW 2 <校验和>
                            └─ engine.applyMove + 播走子动画
                                                    各端 Apply → apply + 播动画 + 比对校验和
```

**先广播、后播动画**是有意的：反过来的话客户端永远比房主晚一整个动画时长，而飞行棋的走子动画是逐格 1 秒、一步可能好几秒，几个回合就累积成明显滞后。

**不做 ack**：命令队列本身保证不丢不乱序，设备快慢的差异表现为某个客户端慢半拍，下一个回合的间隙就吸收掉了。

### engine 自己就一致的东西，一律不发消息

摇 6 的额外回合、无合法走法自动过手、三连 6 的罚回机库、胜负判定与排名——全部在 `GameEngine` 内部由同一串输入推出，四端必然一致。协议里**没有** `TURN_PASSED`、**没有** `GAME_OVER`。少一类消息就少一类不同步的可能。

### AI 只在房主跑

现有 20Hz 轮询 driver 的条件从 `currentTeam != humanTeam` 改成「当前座位是 AI 或托管中」，并整体加一个「仅单机或房主」的门。客户端上它完全不启动。房主跑完 AI 的 roll + move 后照常入队、广播。`PlaneAi` 与其调用代码不改。

### 本地输入的双重门禁

客户端发出 `ROLL_REQ` 后到 `ROLLED` 回来之前锁住本地输入（防连点）；房主侧同时对 `phase` 和「这条连接是不是当前队伍」做校验，不合法的请求静默丢弃（局域网内是可信设备，不因一次校验失败断连）。

### 再来一局

结算后回**大厅**而不是直接重开——座位表保留，此时可以换座、可以等新人加入，房主再点开始。复用同一套大厅 UI，比单独做一条「联机版再来一局」路径少一整块代码。客户端的结算面板不显示开始按钮，显示「等待房主开始新一局」。

## 掉线与 AI 托管

**检测**：socket 读写抛 `IOException` 即断线，不做应用层心跳。

### 座位状态机

```
  在线 ──断线──▶ 已断线（对局照常跑，不阻塞任何人）
                     │
                     ├─ 轮到他 ──▶ 等待重连（15s 倒计时，HUD 显示「等待 XXX 重连 12s」）
                     │                  │
                     │                  ├─ 重连成功 ──▶ 在线，本回合仍由他自己操作
                     │                  └─ 超时 ──────▶ AI 托管
                     │
                     └─ 不是他的回合时重连成功 ──▶ 直接回到在线，无感
                     
  AI 托管 ──重连成功──▶ 已回归（本回合仍由 AI 打完）──▶ 下一回合起恢复本人操作
```

`RECONNECT_GRACE_S = 15` 是判断值，放在 `RoomState.kt` 里供两侧共用（`SpaceGomoku` 记录过「两份私有副本靠运气保持一致」的教训）。

### 判断与理由

- **只在轮到他时才阻塞 15 秒**。别人的回合他掉着线，对局全速进行，其他三个人完全无感。这正是选「短暂等待后再交给 AI」而不是「立即托管」的意义：瞬断不白白损失一个回合。
- **托管后重连回来，不打断进行中的那一回合**。AI 已经开始摇了就让 AI 打完，下一回合才交还。中途夺权会撞上正在跑的动画和 `isTurnBusy` 门禁，不值得为它开一条新代码路径。
- **重连不设总时长上限，也不弹「继续等待 / 结束对局」**。既然掉线不阻塞别人，就没有必要逼谁做这个选择。客户端每几秒重试一次，直到成功或本人主动退出。
- **重连成功后房主补一条 `SYNC`**，整盘状态重放，不去补算断线期间漏了哪几条。因为 `SYNC` 只在回合之间发送，重连的客户端可能要等到本回合结束才收到——期间显示「正在同步…」，不显示可能已过期的棋盘。
- **房主掉线 = 对局结束**。见「不做的事」。客户端重试失败到一定次数后显示「房主已离开」，回到开始页。

### 边界情况

| 情况 | 处理 |
|---|---|
| 大厅里有人掉线 | 座位直接空出来，别人可以坐进去 |
| 掉线的人重连回来但原座被占 | 房主安排到别的空位；没空位则拒绝，客户端显示「房间已满」 |
| 校验和对不上 | 客户端发 `RESYNC_REQ`，房主在回合间隙补 `SYNC`；同时 `Log.e` 记录，便于事后定位 |
| 四个人全掉线只剩房主 | 剩下三席全是 AI 托管，等价于单机 |
| 房主中途解散 | 广播 `ENDED`，各端回开始页 |
| 客户端在非自己回合点击 | 直接忽略，不发任何消息 |
| 房主收到不合法的请求 | 静默丢弃，不断连 |
| 局域网内同时有多个房间 | 全部列在发现列表里，用户自己选 |
| `BoardStage` dispose / 切后台 | 关 socket、停 NSD 注册与发现、取消所有协程 |

## 测试计划

### JVM 单测（`net/` 全部纯逻辑）

| 测试 | 覆盖 |
|---|---|
| `MatchMessageTest` | 每种消息 `encode`/`decode` 往返；垃圾字符串、字段数不对、非法队伍名一律返回 `null` 而不抛异常 |
| `StateChecksumTest` | 同状态同值；任意一架飞机挪一格、或 `currentTeam` 不同，值必须变 |
| `SeatAssignerTest` | 加入落座、换座裁决（空位成功 / 已占忽略）、开局空位固化 AI、掉线空出座位、重连后原座被占的重新安排、房间已满拒绝 |
| `RelayDiceTest` | 强制点数只生效一次，之后回落到真随机 |

### `MirrorReplayTest` —— 方案 C 的立论本身

在一个 JVM 进程里开两个 `GameEngine`：一个当房主（真骰子），一个当客户端（`RelayDice`）。把房主产生的 `ROLLED` / `MOVED` 消息序列喂给客户端 engine，**每一步之后断言两边 `StateChecksum` 相等**，跑到分出胜负。

项目已有 `SelfPlay.kt` + `SelfPlayHarnessTest.kt` 这套无头自对弈脚手架，它驱动的正是真 `GameEngine`（`roll` / `legalMovesForPendingRoll` / `applyMove` 同一串调用）。fork 一份改成双引擎即可。用几百到几千个随机种子跑，摇 6 连击、三连 6 罚回机库、僚机整体移动、撞墙反弹、飞行捷径、归家小道精确点数等全部规则分支都会被随机自对弈自然打到。

这个测试不碰任何网络、几秒钟跑完，却直接验证了整套设计赖以成立的假设：*同一串骰子点数 + 同一串走子下标，四端必然推出同一个局面*。假设若在某个规则分支上不成立，会在这里被抓住，而不是在多设备对局打了十分钟之后。

### 设备验证

**已确认的环境限制**（不是猜测，是本工作区的实测记录）：

- PICO 模拟器跑在 QEMU 用户态 NAT 上，**模拟器与真机之间双向都不通**，「一台模拟器 + 一台真机」这条路是死的。
- 两个模拟器之间组播同样过不去，**NSD 自动发现在模拟器上无法验证**。
- **真机 `screencap` 直接失败**，真机上拿不到截图，取证只能靠 `logcat`。
- 用户手上**只有一台 PICO 真机**。

因此验证分四层，其中第 3 层是主力：

| 层 | 手段 | 能验 | 验不了 |
|---|---|---|---|
| 1 | JVM 单测 + `MirrorReplayTest` | 协议编解码、座位逻辑、确定性重放 | 任何真实网络 |
| 2 | 模拟器截图（`spatial-design-first-build` 门禁 B） | 三个新面板的布局 | 联机链路 |
| 3 | **真机 + Mac 陪练脚本** | NSD 注册/发现两侧、TCP 链路、完整协议往返、掉线托管、重连、房主离开 | 真机↔真机的真实无线时序 |
| 4 | 两个模拟器 + `adb forward`（手动输 `127.0.0.1`） | 同层 3 的链路部分，作为不占用真机的日常回归 | NSD 发现 |

**第 3 层的具体做法**（真机与 Mac 挂同一路由器）：

- 验 NSD *注册*侧：真机建房 → Mac 上 `dns-sd -B _spaceflightchess._tcp`，确认房间出现。
- 验 NSD *发现*侧：Mac 上 `dns-sd -R "MacRoom" _spaceflightchess._tcp . 47780` 假装有个房间 → 真机的「查找房间」列表里应出现它。
- 验完整链路：`tools/lan_peer.py`（约 100 行）扮演对端——客户端连上真机的房主，或反过来扮演房主让真机加入。它能验建房、加入、换座、开局、完整对局收发，并且**直接 `kill` 掉脚本即可触发掉线托管与重连**。协议是纯文本行让这个脚本成为可能；它同时是一个协议一致性检查器，收到不认识的消息就报错。

第 4 层的 `adb forward` 端口串接是一个**尚未验证的假设**，实现阶段第一步就试；通了作为日常回归手段，不通就全部依赖第 3 层。

**留下的空白**：真机↔真机之间的真实无线时序无法验证，需要第二台头显。交付说明里必须明确标注这一条。

### 日志取证

协议收发的每一条消息、每一次座位状态变更、每一次校验和比对失败，都打 `Log.e(TAG, ...)`（沿用本项目现有的 `SpaceFlightChess:E` 单一 tag 约定），让 `logcat` 本身能还原整条时间线——真机上这是唯一的取证手段。注意 logcat 是 2MB 环形缓冲，复现完要立刻捞。

## 影响范围与风险

**新增** 10 个文件（6 个纯逻辑 + 2 个网络 + 1 个 UI + 1 个 Python 工具），约 1400–1800 行。

**修改** 4 个文件，见「文件清单」。

**兼容性**：单机模式的玩法行为不变，但它的回合驱动代码路径会被改写成走同一条命令队列。这是本次唯一动到既有对局逻辑的地方，因此现有 85+ 个单测必须全绿，且要在模拟器上重新跑一局单机确认没有退化。

**风险等级：中**。两条主要风险：

1. `BoardStage` 的回合门禁历史上出过两次问题，这次改写它虽然是为了让它更简单，但必须小心，且单机回归验证不能省。
2. 双端链路的验证手段依赖第 3 层的 Mac 陪练脚本（新做的东西）和第 4 层的端口串接（未验证的假设）；真机↔真机的时序无法覆盖。

**UI 门禁**：本次新增大厅、房间列表、数字键盘三个面板并改动 `StartPanel`，按项目约定需要走 `spatial-design-first-build` 的两道门禁——实现前把元素表补进 `.spatialsdk/design-contract.md` 并由用户逐项确认（门禁 A），实现后做限时截图验证（门禁 B）。
